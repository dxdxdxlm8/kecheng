kecheng 新服务器压力测试报告

被测机 103.115.56.210（2 核 · 880MB 内存 · 4GB swap · 5Mbps 带宽 · Ubuntu 23.04） ·  测试日期 2026-09-10  ·  测试目标：30 名学生同时访问是否出现 CPU / 内存瓶颈

结论：CPU 和内存都不是瓶颈。真正的瓶颈是 5Mbps 带宽。

  • CPU 完全不是瓶颈 —— 30 人同时完整加载页面，CPU 峰值仅 10.6%；即使把并发推到 300，CPU 峰值也只有 13.5%。
  • 内存完全不是瓶颈 —— 全部测试中可用内存稳定在 394MB 以上，swap 零增长（始终 58MB），node 进程 RSS 稳定在 188–191MB。
  • 瓶颈是 5Mbps 上行带宽 —— 三次独立测量都撞在 4.5–5.0Mbps 这堵墙上。后果是学生首次打开页面时整班约需 10 秒加载完；加载过一次后浏览器缓存一年，之后几乎没有带宽压力。
  • 比带宽更该担心的其实是免费的 LLM/ASR 额度 —— 服务器侧无压力，但免费 API 一旦限流，课堂会直接卡住。

2. 测试方法

压力测试最容易出错的地方是把压测机放在被测机上（测出来的是"生成器 + 应用"抢 CPU），或者被测数据混进公网波动。因此本次做了交叉验证：

  • 权威口径 = 压测机在服务器本机（127.0.0.1 打 nginx），彻底排除公网链路和代理干扰，得到服务器真实处理能力。
  • 带宽口径 = 从旧服务器（香港机房，RTT 11.8ms）向新机拉取，排除"本机国际链路慢"的可能。
  • 旁证 = 服务器侧独立采样 /proc/stat 差分算 CPU、ss 数连接、vmstat 交叉复核，并用 nginx access.log 行数差值确认真实请求数。
  • 压测工具为本项目新增的 scripts/deploy/loadtest.js（零依赖）与 loadtest-monitor.sh（服务端采样）。
流量真实性已验证：单次 30 并发测试中，客户端发出 3,213 请求，nginx 日志增长 3,335 行（客户端 IP 为真实来源 IP），比例约 1:1，不存在流量翻倍或缓存旁路。

4. 带宽：真正的瓶颈

从旧服务器（香港机房，到新机 RTT 仅 11.8ms）向新机拉取静态资源，独立测量三次都指向同一堵墙：

测量方式吞吐说明
旧机 → 新机，单连接1.10 Mbps单流被压得很低
旧机 → 新机，20 并发聚合4.52 Mbps聚合也上不去，撞上限
本机 → 新机，30 并发（两次）4.9 / 5.0 Mbps跨网 30 并发同样封顶 5M
本机 → 新机，60 并发4.9 Mbps并发翻倍，吞吐纹丝不动 → 确认是硬上限
服务器本机 → 本机（无公网）20.7 Mbps处理能力远超 5M，瓶颈只在出口带宽
怎么判断这是"服务器带宽"而不是"我这边网慢"？ ①并发从 30 翻到 60，吞吐一动不动，说明是被限速而非拥塞； ②换成同城低延迟的旧服务器去测，同样是 4.5Mbps； ③服务器本机自测能跑到 20.7Mbps。 三条合起来只能得出一个结论：这台机器的上行被限在 5Mbps，与客户端无关。

开 gzip 后从 652KB 压到 187.5KB，省了 72%。

好消息：静态资源已经带了 Cache-Control: public, max-age=31536000, immutable。 也就是说这 187.5KB 每人只下载一次，之后一年内不再重复下载；第二节课起，每人每次只传约 3.3KB 的 HTML， 30 人合计 100KB，瞬时完成。冷加载的 10 秒只在"全班第一次打开"时发生一次。

7. 建议（按优先级）

P0 · 正式上课前必须确认的两件事（与本次压测无关，但风险更高）

  • 备用 LLM 配置。当前 LLM/ASR 跑在免费额度上（ModelScope + SiliconFlow）。30 人同时聊天对服务器几乎无压力（SSE 只传文字，几百 KB），但免费 API 一旦限流或停服，课堂会立刻卡死。这是整套系统里最脆的一环，比 5M 带宽严重得多。
  • 学生上传图片的带宽。nginx 允许单张 25MB。30 人同时上传一张 2MB 的解题照片就是 60MB，在 5Mbps 下需要 约 96 秒。如果课堂有"拍照上传"环节，建议提前压图（客户端压缩到 300KB 以内）。

P1 · 把静态资源交给 nginx 直出（顺手能做的事）

当前 nginx 的 location / 把 /_next/static/* 也一并转发给了 Node。虽然它不影响带宽（带宽是硬上限），但能让 Node 少扛一大块活：

  • 加一段 location /_next/static/ { alias /opt/kecheng/.next/static/; expires 1y; access_log off; }，让 nginx 直接读磁盘返回，跳过 Node 进程。
  • 收益：Node 的 CPU 与连接数进一步下降，高并发下响应更稳；但不会改变 5Mbps 这个上限，别指望它解决冷加载 10 秒。

P2 · 如果"首屏 10 秒"不能接受

  • 升级带宽到 10–20M：最直接，冷加载 10 秒 → 约 3–5 秒。
  • 挂 CDN：静态 chunk 走 CDN，机房出口只出 HTML。注意本域名 DNS 在 Cloudflare，把静态资源走 CF 代理即可，但需按中国内地访问质量实测。
  • 拆分首屏 chunk：目前单个 05efca57d55136fd.js 就占 70KB（gzip 后），是首屏最重的一块。若其中有非首屏代码，可做动态 import 拆出去。这属于前端优化，工作量较大。

P3 · 内存与构建

  • 运行时 1G 完全够。所有测试中可用内存从未低于 394MB，swap 一次都没动过。日常运行不是问题。
  • 但构建期是刀尖。发版编译时可用内存最低只剩 27–35MB（见迁移手册实测），虽然没 OOM 但极其勉强。发版一律避开上课时段，或临时加 swap。

8. 附：为什么"看着像 50% CPU"的那几组数据不可信

测试中出现过一组异常读数：从本机直连压测时 CPU 显示 40–60%，而同一时刻换成"服务器本机压测"或"经由本地脚本编排"，CPU 只有 8–13%，且服务端连接数从 30 变成 0。

交叉验证后确认：

  • 两种方式下，服务端 nginx 日志记录的真实请求数一致（客户端 3,213 → 服务端 3,335），不存在流量翻倍；
  • 服务器本机压测能跑到 185–230 请求/秒，此时 CPU 仅 8–13%，内存无变化——这才是服务器的真实处理能力；
  • 那组 40–60% 的读数来自本机出网路径（本机网络带透明代理，连接行为与真实浏览器不同），不代表服务器负载。

因此本报告所有容量结论均以"服务器本机压测"为准，并已用 vmstat、ss、nginx 日志三方交叉复核。
